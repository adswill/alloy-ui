# Decisions

1. **Crate names**: `alloy-ui-{core,layout,render,theme,widgets,platform,ipc,cli}`; all returned 404 on crates.io on 2026-11-20. Directory names are short (`crates/core`).
2. **Geometry, DrawCommand and Event live in core.** Layout, render and widgets all need them; a separate types crate adds a hop for no gain yet.
3. **Widgets draw into a `DrawList`, not a generic renderer.** Keeps the renderer swappable and tests headless. Cost: no per-widget custom GPU pipelines; revisit if needed.
4. **Zero dependencies in the contract stubs.** wgpu, winit, cosmic-text etc. are added by the crates that own them.
5. **Release profile is size-first** (opt-level z, fat LTO, panic abort, strip) to hit the 10 MB counter target.
6. **Visual direction**: follow Impeccable's AI-slop catalogue; see DESIGN.md.
7. **Facade crate `alloy-ui`** (`crates/alloy`) owns the glue: shell events -> `Runtime` -> `WindowRenderer`, background futures through `ipc::TaskRunner` whose waker is the shell proxy. Apps depend on it only. Layouter is a parameter so core stays independent of the layout crate.
8. **Platform PR #1 merged locally by the lead**, verified fmt/clippy/tests on Linux only; Windows and macOS await CI.
9. **Contract change (lead):** `DrawCommand::Text` gained `weight` and `line_height`; new `DrawCommand::Line` for strokes (renderer draws it as a chain of round dots for now; a proper SDF segment is a later optimisation). `Event::Tick(ms)` plus `Widget::animating()` give widgets a timer only while something animates; `Outcome.tick` tells the shell to schedule ~16 ms ticks, so an idle app has no timer.
10. **Weight/line_height are accepted but not yet honoured by the renderer** (ignored with `_`); tracked for the render follow-up along with real text metrics.
11. **Platform: multi-window keys are chosen by the caller** (`WindowKey(u64)`, `MAIN` = 0), so the app, facade and shell agree on identity without a mapping step. Windows are created at the end of the callback that asks for them. The loop exits when the last window closes.
12. **Platform: Wayland clipboard uses data-control, not `wl_data_device`**, over its own connection, via `wayland-client` plus the generated protocol crates `wayland-protocols` and `wayland-protocols-wlr` (same family; no GUI toolkit). Reason: see crates/platform/README.md. Tested against sway 1.9 only.
13. **Platform: Windows file dialogs use the `windows` crate (0.58)** for COM interfaces; `windows-sys` has no interface wrappers and hand-written vtables would be untestable here. Menus, tray and clipboard stay on `windows-sys`.
14. **Platform: accessibility is a platform-neutral tree plus one adapter per OS, no AccessKit.** `access.rs` defines `AccessTree`/`AccessNode`/`AccessRequest` (own types, so `alloy-ui-platform` does not depend on the widgets crate; the facade maps `widgets::A11yNode` onto them). `ShellContext::set_accessibility(&tree)` is called after each frame; adapters diff against the last tree and publish only changes. Screen-reader requests (press, focus, set value, increment, decrement) come back as `PlatformEvent::Accessibility { window, request }`. Linux speaks AT-SPI2 over the crate's own D-Bus client (`dbus.rs`), macOS subclasses `NSAccessibilityElement` and adds a mouse-transparent `NSView` over the content view, Windows subclasses the HWND and answers `WM_GETOBJECT` with UI Automation providers (uses the `windows` crate, see 13).
15. **Platform: key events are dropped while an IME preedit is showing.** winit can still deliver raw `KeyboardInput` during composition on some backends; the shell tracks the preedit state and swallows those events so a widget never sees Backspace or Enter that the IME already consumed. The commit arrives as `TextInput`.
